# Admin Market and Cluster Dashboard Design

## Goal

Deliver a coherent 8/7 admin experience using the supplied `system_web` visual system. Administrators use one Market to discover and install products, one installed-services view to operate them, one record center to investigate activity, and a dashboard that adapts to cluster role.

## Scope

### Canonical navigation

The admin navigation contains these nine destinations:

1. Control center
2. Install packs
3. Customer management
4. API keys
5. Cluster management
6. Test center
7. Record center
8. System environment
9. System settings

Test center exposes API playground, API documentation, and benchmark testing. Record center exposes execution history, API records, background jobs, service records, and system records.

`admin/_layout.php` is the only admin app shell and navigation source. It loads the supplied `system_web` design tokens, app shell, dashboard, and pack styles after they are adapted into the existing asset tree. Pages do not duplicate the header or navigation markup.

All new user-facing admin text is added to and rendered through the existing i18n system. This includes navigation labels, tabs, category labels, count labels, empty states, disclosure labels, role labels, notices, and legacy-debug notices. Stable technical contract fields such as `pack_id`, `mode`, `runtime_level`, and `endpoint` remain English.

Pack purpose copy is an i18n seed keyed as `pack.<pack_id>.description`. Market cards render that Chinese/localized copy and fall back to the existing manifest description only when a seed is absent. Purpose copy is never duplicated in page templates.

PHP `__()` remains the dictionary source of truth. A dynamic client interaction may receive a small page-scoped i18n dictionary generated by PHP and cache it in memory for the page lifetime. It must not introduce a second translation endpoint or persistent browser cache.

All admin runtime assets are local. The supplied CSS, logo, and bundled vendor JavaScript are copied into the project asset tree. Any font used by the new shell is self-hosted with `@font-face` and a system-font fallback; no admin page loads JavaScript, CSS, images, or fonts from a CDN.

### Site branding

System Settings gains a small Branding section beside the existing site title and subtitle settings. A system administrator can upload a replacement site logo, preview the active logo, or restore the bundled default. The selected logo is used by the admin app shell, login page, and metadata/favicon surfaces that already render the site identity.

Branding reuses storage settings and the existing validated-image upload pattern; it does not add a branding table. Upload accepts only PNG, WebP, and JPEG after server-side MIME and image validation, with a bounded file size and dimensions. SVG is rejected. A new file is validated and stored before it replaces the active setting, old managed branding files are removed only after a successful replacement, and a single helper/served endpoint resolves the active logo. Templates never accept a user-controlled asset path.

## Release identity and update visibility

The release identifier is a date build ID: `YYYYMMDDNNN`. The machine-readable value is stored as `HUB_VERSION`; the UI formats it as `YYYY.MM.DD.NNN`. For example, this development build is `20260729001` and the 8/7 demonstration freeze target is `20260807001`.

Windows WSL remains a supported authoring and validation environment. Development may be committed frequently after focused tests so Linux and WSL behavior can be compared early. That workflow is separate from deployment: the 3wa integration host is the only normal Git push source, while the 5090 and 1080 execution nodes fetch and fast-forward or check out an immutable release tag. Execution nodes do not push.

Before the 8/7 demonstration, create and deploy an immutable `20260807001` release tag. Every participating host reports the same release tag/commit, Pack inventory, runner image digest, and health result.

System Environment provides a read-only update view: current release ID, commit, clean/dirty worktree state, available remote release, and each child station's release/health compatibility. A station with a mismatched release or Pack contract is visibly marked as needing update and is not silently presented as equivalent to current stations.

System Settings may show the recommended CLI update command but does not execute `git pull` or deploy code from the browser in this release. Automatic rollout, migrations, canary sequencing, rollback, and independent Pack version/digest rollout are explicit non-goals for 8/7 and belong to a later enterprise maintenance platform.

### Market and installed services

`admin/marketplace.php` becomes the canonical Market endpoint with two workspaces:

- `market`: discover Pack products and their model requirements.
- `services`: operate installed services.

The Market retains the supplied dense category tabs and live counts:

- All
- Reference
- Vision
- Language
- Audio
- Tools
- Experimental

Counts are derived from existing Pack catalog and manifest data. Every Pack maps to exactly one Market category, including Experimental, so category counts have no overlap and their total equals All. A product card shows the product identity, localized short purpose, runtime level, CPU/GPU requirement, and local installation state. Model readiness and technical Pack fields are secondary detail, expanded only when requested.

The installed-services workspace reuses the existing service actions and background command jobs. Each service shows its name, Pack, mode, enabled state, runtime/health state, and start/stop/enable controls. Endpoint, runtime contract, configuration state, and recent job detail remain collapsed by default in a native `details` disclosure. Existing state codes retain their backend meaning but resolve to localized display labels, including Queued (排隊中), Starting (啟動中), Running (執行中), Stopped (已停止), Unhealthy (異常), and Failed (失敗). Destructive or disruptive operations keep their existing confirmation and background-job behavior.

`admin/packs.php`, `admin/models.php`, and `admin/services.php` are removed from all visible navigation and documentation. They remain reachable as hidden legacy-debug pages during the 8/7 transition, carry a `@deprecated` canonical URL note, and retain a minimal response smoke test. The new Market reads existing application helpers and never includes or copies legacy controller HTML.

### Record center

`admin/log_explorer.php` is the canonical Record Center. Its tab order is:

1. Execution history
2. API records
3. Background jobs
4. Service records
5. System records

Execution history reuses the existing `runtime_runs` data and detail links. API records reuse the existing access-log filters and queries. Background, service, and system records reuse the existing log center data sources.

`admin/api_usage.php` and the runtime-run list endpoint become hidden legacy-debug pages, not redirects. The normal UI has no links to them, while their direct URLs remain available for temporary diagnosis.

### Role-aware cluster dashboard

Dashboard behavior follows the local cluster role:

- A unified entry router renders station tabs using `cluster_stations.display_name` (site title), including the local self station when it exists. It never calls the tabs GPU 1, GPU 2, or GPU 3.
- A child entry node renders only its own host, GPU, queue, Pack, and health information. It does not render multi-station tabs or imply it schedules other hosts.
- Cluster management remains responsible for pairing, tokens, station enablement, published modes, and refresh. Dashboard is an observation and navigation surface, not a configuration form.

Station tab content uses existing station inventory/status data: freshness, health, VRAM, GPU leases, queued/running work, published modes, active routes, and supplied services. Site title is primary; hardware is supporting metadata.

When the router role is enabled, the existing `scripts/cluster_refresh.php` is installed as the only periodic health mechanism. A router-side cron invokes it once per minute and logs its result. Child nodes do not gain a new push/reporting protocol. The station freshness window is set to 90 seconds so a normally scheduled one-minute refresh remains fresh through ordinary cron jitter; an interactive router request may still refresh a station immediately under its existing behavior. Dashboard visibly shows last refresh time and stale/offline state.

### Aggregate station reservation

This release reserves display support for a future aggregate station (a Router that can later be attached to an upstream Router) without implementing hierarchical routing.

The dashboard view model computes, rather than persists:

- `aggregate`: local router and child-node roles are both enabled.
- `children_count`: current paired child stations.
- `published_mode_count`: aggregate published modes.

The UI may label such a station as an aggregate station and show its child count. It does not add a database table, upstream pairing field, token exchange, route-path field, hop limit, or cross-layer forwarding. Those are a separate future routing/security project.

## Migration and retirement

The canonical views are introduced first. Legacy pages are hidden, documented with their canonical replacement, and covered by narrow availability checks. Once the 8/7 release has been stable, their controllers and tests can be removed in a later dedicated cleanup change.

No new product, model, service, log, or cluster tables are introduced for this redesign.

## Validation

- Navigation exposes exactly the agreed top-level destinations and grouped menus.
- Market category counts and local install/readiness labels match catalog, manifest, model, and service data.
- Installed-service actions still enqueue the existing command jobs; collapsed details do not hide required controls or errors.
- Record Center tabs retain existing filters and detail links.
- Router dashboards use station titles; child nodes have no multi-station switcher; aggregate labels derive from existing role/inventory data.
- Legacy debug URLs remain available but are absent from normal navigation.
- New visible labels and notices resolve through the existing i18n seed and language selector; technical contract identifiers stay stable in English.
- Branding upload, preview, restore-default behavior, invalid image rejection, and default-logo fallback are covered by admin-only tests.
- Release ID formatting, read-only update reporting, and station release/Pack mismatch visibility are covered without executing Git operations from HTTP requests.
- Desktop and mobile rendering follow the supplied `system_web` app shell, pack tab density, and dashboard layout without duplicated CSS or navigation markup. Screenshot verification is a release gate: capture desktop and mobile states, inspect overflow, text clipping, color contrast, tab/detail states, and template fidelity, then adjust CSS and recapture until the issues are resolved.

## Explicit non-goals

- Hierarchical or upstream cluster forwarding.
- New cluster credential formats or route-loop prevention.
- A new model-download subsystem.
- A second admin API or duplicate page-specific data layer.
